# Развитие TimeTrack Pro — PPL Group

## Текущее состояние: 0.3.0

Есть локальный цикл двух синтетических Excel: генерация, загрузка, ETL ФИ, псевдонимизация, расчёты, просмотр, роли, восстановление ФИ в выгрузке. Интерфейс опирается на предоставленные скриншоты, вход — на композицию «Портал» из HTML. Скриншоты не являются функциональным ТЗ для интеграций.

В 0.2.0 выполнен перенос интерфейса на React + TypeScript + Vite. Backend остаётся Python/FastAPI. Next.js не используется и больше не является обязательным этапом: он понадобится только при появлении отдельного обоснованного требования. Завершён перенос загрузки, фильтров, табличных экранов, аналитики, персональной детализации и выгрузок. В 0.3.0 выполнена модульная реорганизация backend и frontend, добавлены фабрика приложения, интерфейс репозитория и согласованная публикация снимков. Описание — docs/Architecture.md. Дальнейшие работы ниже не входят в 0.3.0.

## Этап 1. Приёмка тестового сценария

Пройти Steps.md на Windows. Утвердить размеры таблиц, расположение фильтров, состав колонок, коды, дефолтные периоды, трактовку присутствия. Зафиксировать замечания с ожидаемым результатом, скриншотом и тестовой парой. Критерий: пользователь самостоятельно получает отчёт из двух файлов.

## Этап 2. Надёжный импорт реальных форматов

Добавить профили для «План_Офис.xlsx», месячных листов и исходной выгрузки СКУД, выбор листа, поиск шапки и границ таблицы, пропущенные календарные дни, слитые колонки. Оригинальные ячейки неизменны, каждое преобразование имеет ссылку на источник. Контроль месячных и подневных итогов СКУД. Ошибки импорта показываются адресами ячеек без потери строк. Ограничить XML/ZIP ресурсы, обрабатывать формулы с отсутствующим кешем явно.

Приёмка: утверждённые образцы каждого профиля дают ожидаемое число сотрудников и независимые контрольные суммы; неподдержанный формат не выдаёт ложный успех.

## Этап 3. Разрешение неоднозначности идентификации

Реестр сотрудников со стабильным внутренним ID и версиями ФИ. Интерфейс конфликтов, ручное подтверждение соответствия, запрет автоматического объединения однофамильцев. ФИ остаётся единственным общим входным признаком, но совпадение одинаковых ФИ у разных людей нельзя решить алгоритмически без дополнительного проверенного источника. Опечатки допускаются только как предложения оператору. Каждое решение аудируется.

Приёмка: ни одна неоднозначная пара не участвует в расчётах без подтверждения; правило можно отменить и воспроизвести.

## Этап 4. Календарь и методика учёта

Версионируемый производственный календарь с праздниками и переносами, нормы часов, неполная занятость, изменения подразделения во времени. Утвердить правила перерывов и ночных смен. Отдельно хранить присутствие, подтверждённое рабочее время и удалённую работу. Опоздания рассчитывать только при наличии нормативного времени начала и допуска. Не выводить эффективность труда из длительности проходов.

Приёмка: набор граничных случаев (февраль, праздники, ночная смена, неполная пара) рассчитан по согласованным примерам.

## Этап 5. Развитие React и PostgreSQL

Развивать существующие React/TypeScript-компоненты с сохранением согласованного дизайна; после пользовательской приёмки добавить серверную пагинацию и виртуализацию больших таблиц. FastAPI оставить единственным владельцем правил доступа и расчётов. PostgreSQL: employees, departments, memberships, import_batches, plan_days, access_days, match_decisions, report_versions, audit_events. Справочник персональных данных и ключи держать отдельно от аналитических таблиц. Импорт транзакционный, идемпотентный, с версией и отпечатком источников. Фоновые задания добавлять по фактической длительности обработки, а не заранее.

Локальное развёртывание Windows; Docker Compose — после проверки удобства запуска у пользователя. Никакого hosting.json и внешнего хостинга без отдельного решения.

Приёмка: повторная загрузка не дублирует данные; параллельные пользователи не видят промежуточное состояние; предыдущую версию можно восстановить.

## Этап 6. Полный RBAC и управление пользователями

Экран администрирования, назначение нескольких подразделений, запреты на отдельные поля и экспорт, отзыв сессий, смена пароля, восстановление доступа, более строгий аудит. Защищённое хранение ключа отдельно от данных и тест восстановления резервной копии. Пересмотреть доступ аудитора по утверждённой матрице: сейчас он получает псевдонимы.

Приёмка: негативные тесты для всех 7 ролей, включая подмену ID/фильтра/ссылки на скачивание. Скрытие кнопки само по себе не считается контролем.

## Этап 7. Отчётность и эксплуатационная готовность

Полные персональные карточки, версия правил в каждом отчёте, отдельные отчёты по офису и отделам, печатные шаблоны, фильтры, зафиксированная дата анализа. Политика хранения и очистки снимков, история периодов, закрытие месяца, согласования и ручные корректировки — после утверждения процесса. Проверка UX при 100%, 150%, 200% масштабировании и на мобильном. Подписанный Windows-пакет, офлайн-набор зависимостей, резервное копирование, обновление и откат.

Приёмка: автоматические тесты, браузерные сценарии, восстановление из резервной копии, сверка Excel, отсутствие секретов в релизном архиве.

## Отдельный будущий контур

Прямая интеграция RusGuard, почта, 1С, Т-13, дополнительные источники и облачное развёртывание не входят в текущую очередь. Каждому нужны отдельные требования, полномочия и критерии приёмки. Сроки можно оценить после завершения первой проверки и уточнения реальных входных форматов.
