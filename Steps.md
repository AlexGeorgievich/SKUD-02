# Шаги работы и приёмки

Актуальная версия: 0.3.0, React + TypeScript + Vite / Python FastAPI.

## 0. Зафиксированные требования

TimeTrack Pro, заказчик PPL Group. Только два источника: план и СКУД_факт. План — ключевой. Для первой проверки — синтетические данные Faker. Скриншоты используются как дизайн-референс. ZIP для локального запуска, без облачного хостинга.

## 1. Подготовка

Распаковать архив, проверить Python 3.12+, запустить start.bat, создать пароль администратора. Успех: сервер запущен на 127.0.0.1:8000 и доступен экран входа. Если установка прервана — выполнить команду установки из README.md; не вводить рабочие данные в тестовую версию.

## 2. Проверка тестового набора

Открыть demo/plan.xlsx и demo/skud_fact.xlsx. Ожидаются август 2026, 31 день, 166 сотрудников, 17 отделов плана. В плане отделы объединены и повёрнуты; в СКУД заголовок в строке 9, сортировка по фамилии, итоги с длительностями свыше суток. ФИ с изменённым регистром и пробелами — намеренный тест.

## 3. Загрузка

Выбрать август 2026. Перетащить каждый файл в свою область, затем повторить через кнопку выбора. Проверить отображение имени файла. Нажать «Проверить и просмотреть»: 166/166, первые 8 строк обоих источников. При выборе другого месяца импорт должен остановиться с понятной ошибкой. Поменять файлы местами: должна сработать проверка заголовков.

## 4. Обработка

Нажать «Обработать план–факт». Ожидаются 166 сотрудников, 5146 строк детализации, 0 лишних сотрудников факта для комплектной пары. На дашборде есть ненулевые замечания. Повторный импорт той же пары даёт те же расчёты и заменяет, а не добавляет набор.

## 5. Просмотр

Открыть План, Факт, План-факт, За месяц, Проверку данных. Выбрать HR: 4 сотрудника; Buying: 39. В табличных экранах найти сотрудника по ФИ. Нажать строку, проверить окно замечаний, перейти «По дням». Убедиться, что горизонтальная и вертикальная прокрутка оставляют заголовки и сотрудника видимыми.

### 5а. BI-дашборд и карта замечаний

1. Открыть «Дашборд» без фильтра отдела. В «Структуре офиса по штату» проверить Treemap и список всех отделов; плитки должны занимать всю область пропорционально численности.
2. В широком окне открыть «Карту замечаний»: должны быть видны все дни календарного месяца, для августа — `01`–`31`. На узком окне допускается горизонтальная прокрутка без скрытия названий отделов.
3. Нажать цветную ячейку карты. Ожидается модальное окно «Расшифровка замечаний · <отдел> · <дата>» с таблицей: сотрудник, план, факт СКУД, приход, уход, часы, замечание. Ячейка без замечаний не открывает окно.
4. Нажать `Esc`, затем повторить через «Закрыть ×». Окно закрывается, отдел и текущий экран не меняются. Отсутствие регистрации трактуется как запись для проверки, а не как прогул.
5. Выбрать отдел. Проверить Treemap «Структура плана», легенду из шести статусов под ним и панель «Распределение часов присутствия». Её интервалы описывают известное время СКУД, не продуктивность.

## 6. Excel и печать

С дашборда выгрузить полную книгу: 4 листа. В «За месяц» ожидается 166 строк данных плюс заголовок. Сравнить часы сотрудника с суммой доступных дневных интервалов. Повторить экспорт при фильтре HR: 4 строки данных. Проверить экспорт из карточки одного сотрудника. Нажать печать и сохранить PDF средствами браузера, проверить переносы страниц на своём устройстве.

## 7. Исключения

На копии плана сделать два одинаковых нормализованных ФИ — импорт останавливается. Удалить строку сотрудника из факта — сотрудник остаётся в плане с замечанием. Внести неверное время и несовпадающий итог дня — видна проблема. Удалёнка без прохода не помечается как неявка. Будущие дни без проходов не считаются нарушениями. Исходные тестовые файлы для повторения сохранить неизменными.

## 8. Права

Создать руководителя HR по README.md: видит только 4 сотрудников, импорт запрещён. Экспорт другого отдела по изменённому URL не выдаёт чужие записи. Создать сотрудника по точному ФИ: только своя запись. Аудитор видит псевдонимы и журнал, не выполняет импорт. Выход завершает сессию; повторный запрос данных без входа запрещён.

## 9. Автоматическая проверка сборки

Команда: `python -m unittest discover -s backend/tests -t . -v`. Проверяет численность, високосность, нормализацию, несовпадение периода, дубли, неполные интервалы, расчёты и отсутствие ФИ в аналитическом JSON, восстановление имён в Excel, будущие дни, удалёнку, вход, импорт, экспорт и ограничение руководителя.

Статус выполнения в среде сборки будет зафиксирован в TEST_RESULTS.md. Проверки браузерного drag-and-drop, Windows-запуска и печати требуют приёмки на компьютере пользователя; они не выдаются за автоматически пройденные.

Дополнительно для React: из папки `frontend` выполнить `npm ci`, `npm run build`, `npm test`. Компонентные тесты имитируют drop, выбор файлов, отправку пары через multipart, блокировку повторного действия, фильтрацию и ошибку входа. Это проверки в jsdom, не браузерные E2E-тесты.

## 9а. Приёмка переноса на React

1. Запустить `start.bat` без Node.js: используется готовая сборка из архива. Успех: доступен обновлённый экран входа и пометка версии 0.3.0 в меню.
2. Загрузить август 2026 двумя способами. Во время обработки кнопки повторного импорта и смены периода недоступны. Успех: 166 сотрудников, результат загружен без перезагрузки страницы.
3. Открыть «За месяц», перейти на вторую страницу; убедиться, что поиск находит сотрудников по всему набору. Изменить отдел: пагинация возвращается на первую страницу.
4. Применить поиск, скачать Excel: выгрузка соответствует выборке. Проверить кнопку «Без ФИ» и обычный экспорт.
5. Открыть окно сотрудника клавишей Enter по имени, переключить «По дням», закрыть Escape. Проверить доступность кнопок с клавиатуры и прокрутку.
6. Использовать кнопку «Печать» приложения: она раскрывает всю отфильтрованную таблицу, а не только первые 100 строк. Проверить в предварительном просмотре браузера.
7. Проверить выход и повторный вход, сохранение последнего результата после перезапуска Python, роли руководителя, сотрудника и аудитора.

## 9б. Проверка модульной сборки

1. Проверить наличие `backend/app`, `backend/tests`, `frontend/src/features` и `frontend/dist`.
2. Запустить `start.bat`; открыть `/api/health`: версия 0.3.0.
3. Повторить полный цикл двух файлов и перезапустить сервер: активный результат сохраняется.
4. Для переноса старых данных остановить сервер и скопировать всю папку `data` согласно README. Убедиться, что результат читается до нового импорта. После импорта появляется `data/current.json`.
5. При резервном копировании остановить сервер и копировать всю папку `data`, включая ключ и снимки.

## 11. Кадровый контур

1. Скопировать `.env.example` в `.env`, задать `POSTGRES_PASSWORD`, выполнить `docker compose up -d --build` и проверить `docker compose ps`.
2. Импортировать пару «План + СКУД»: после успешной публикации снимка сотрудники из плана появляются в PostgreSQL. Повторный импорт обновляет только ФИО/отдел плановой синхронизацией, кадровые поля не перезаписывает.
3. Открыть «Кадровый учёт → Реестр». Нажатие по строке открывает карточку; источник ФИО и отдела помечен «План». Для роли `hr` изменение должности сохраняется и попадает в `hr_audit_log`.
4. На вкладке «Аналитика» проверить численность по отделам, сотрудников вне текущего плана и незаполненные карточки.
5. На вкладке «Импорт HR» выполнить preview, убедиться, что ошибка/недопустимое поле не меняет данные, затем явно применить исправленные безопасные поля. Роли `manager`, `employee`, `auditor` получают отказ на изменение и импорт.

Для каждого замечания записать: шаг, входной период, роль, действие, ожидаемый результат, фактический результат, скриншот и синтетическую пару файлов. Критические: утечка чужих данных, неправильная связка ФИ, потеря сотрудников, неверные суммы. Удобство/оформление фиксировать отдельно. Следующий этап выбирать по Plan.md только после приёмки текущего.
